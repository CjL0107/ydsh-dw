## 一、这套编排要解决什么问题

第 1~3 周的部署是「一个容器一个命令」堆出来的：先 `docker run mysql`，等它起来，
再 `docker run hive-metastore`，再 `docker run hive-server`，中间还得手工判断
"到底起没起来"。这套做法有三个硬伤：

1. **顺序靠人记**。Metastore 比 MySQL 早起来 2 秒，`schematool -initSchema` 就会失败，
   而失败信息是 `Communications link failure`，看起来像网络问题。
2. **密钥散在命令历史里**。`docker run -e MYSQL_ROOT_PASSWORD=root` 这种命令一旦
   进到 shell history 或文档里，等于把口令公开了。
3. **换个机器就得重来一遍**。验收、答辩、换笔记本，每次都要重新回忆那串命令。

第 4 周把 7 个服务收进一份 `docker-compose.yml`，用
`depends_on + condition: service_healthy` 把顺序写成代码，用 `.env` 把密钥抽出来。
目标是一句话：**`docker compose up -d`，然后所有服务自己按正确顺序就绪。**

## 三、首次部署

### 3.1 前置条件

- Docker Desktop 已启动（`docker info` 能返回 Server Version）
- 内存分配 ≥ 6 GB（Hive + Tez + Superset 同时跑，4 GB 会 OOM）
- 首次部署需要联网拉镜像（约 3.5 GB）

### 3.2 配置密钥

```bash
cp .env.example .env
```

然后按需填写。三个必须自己生成的值，用这条命令生成（不要手打弱口令）：

```bash
python -c "import secrets; print(secrets.token_hex(12))"
```

`.env` 里各变量的作用：

| 变量 | 必填 | 说明 |
|---|---|---|
| `MYSQL_ROOT_PASSWORD` | 是 | MySQL root 口令；Metastore 与 Superset 共用 |
| `METASTORE_DB` | 是 | 元数据库名，默认 `metastore` |
| `CLICKHOUSE_USER` / `CLICKHOUSE_PASSWORD` | 是 | ClickHouse 口令。**不设会报 516 Authentication failed** |
| `CLICKHOUSE_DB` | 是 | 默认 `ydsh_ads` |
| `SUPERSET_SECRET_KEY` | 是 | 会话签名 + 数据源口令加密。**缺失时 compose 直接报错退出**（故意设计） |
| `SUPERSET_ADMIN_PASSWORD` | 是 | 仅首次 `create-admin` 生效；账号已存在时不会覆盖 |
| `SUPERSET_PORT` / `APP_PORT` / `STREAMLIT_PORT` | 否 | 默认 8088 / 8000 / 8501 |
| `REFRESH_TOKEN` | 建议 | `/api/refresh` 的访问令牌；留空则不校验 |
| `LLM_API_KEY` 等 | 是（问答功能） | 第 3 周的大模型配置，Streamlit 问答要用 |

> ⚠️ **`.env` 必须存成 LF 行尾**。Windows 记事本存成 CRLF 时，值末尾会带一个
> `\r`，Docker 原样传给容器 —— 表现出来就是「密码明明是对的，登录却提示无效」。
> 我在部署时真踩了这个坑：`SUPERSET_ADMIN_PASSWORD` 尾部带着 `\r`，
> reset 口令时把 `\r` 一起写了进去，登录页一直报「无效的用户名或密码」。
> 排查方法：`python -c "print(open('.env','rb').read().count(b'\r'))"`，结果是 0 才对。

## 五、故障排查（都是这次真实踩到的）

### 5.1 `ports are not available: 0.0.0.0:8501 bind: Only one usage of each socket address`

宿主机上已经有一个进程占着 8501 —— 我是之前为截图手工起的
`python -m streamlit run apps/streamlit_app.py` 还在跑。

```bash
netstat -ano | grep LISTENING | grep :8501     # 拿到 PID
# 确认是那个临时进程后结束它
powershell -c "Stop-Process -Id <PID> -Force"
docker compose up -d streamlit
```

### 5.2 `ValueError: Invalid decryption key`

Superset 元数据库里存的数据源口令是用 `SECRET_KEY` 加密的。**换 `SECRET_KEY` 之后
旧密文解不开**，日志里刷这个异常，图表连不上库。

- 这台机器：把 `.env` 的 `SUPERSET_SECRET_KEY` 改回元数据当初用的那个值即可。
- 生产环境换 key 要走 `superset re-encrypt-secrets`，并配置 `PREVIOUS_SECRET_KEY`，
  否则必须先备份元数据库。

> 结论写进规范：`SECRET_KEY` 必须**一次定终身**，不能在运行期随意轮换。

### 5.3 pyhive 报 `TTransportException: TSocket read 0 bytes`

不是网络不通，是**认证方式不匹配**。`HIVE_AUTH=NOSASL` 会让 pyhive 裸 thrift 握手，
本项目的 HiveServer2 是 `authentication=NONE`，服务端不认。

- 正确配置：`HIVE_AUTH=NONE`
- 但 `NONE` 模式下 pyhive 仍要建 SASL/PLAIN 通道，镜像里必须装 `thrift-sasl`
  （缺了报 `No module named 'thrift_sasl'`）。用 `pure-sasl` 而非 `sasl`，避免编译 C 扩展。

### 5.4 `pip install` 在构建阶段 `ReadTimeoutError`

直连 `files.pythonhosted.org` 会 15 秒读超时，一次构建白等 6 分钟还失败。
Dockerfile 里已改用清华源，并通过 `PIP_INDEX_URL` 构建参数暴露出来：

```bash
docker compose build --build-arg PIP_INDEX_URL=https://pypi.org/simple app
```

### 5.5 `hive-server` 重启后 Exited(1)，日志 `HiveServer2 running as process 7. Stop it first.`

镜像把进程号写进 `/opt/hive/conf/hiveserver2.pid`，该文件残留在容器可写层；
新容器的入口 bash 恰好也是 PID 7，脚本误判服务已在运行就直接退出。
编排里的 `entrypoint` 先 `rm -f` 这个文件再 `exec` 原入口，已根治。**不要删这行。**

### 5.6 ClickHouse `516 Authentication failed`

默认用户无密码时 ClickHouse 拒绝登录。编排里显式注入了
`CLICKHOUSE_USER / CLICKHOUSE_PASSWORD`，同步脚本也改成**从 `.env` 读、不再有默认口令**，
缺失时直接报错退出，避免"用错口令连上去查空表"这种更难查的问题。

### 5.7 容器里报 `No module named 'openai'`（宿主机却正常）

`nl2sql` 走 OpenAI 兼容协议，宿主机早就装了 `openai`，镜像的
`requirements.txt` 里漏了。这类"本地好好的、容器里挂"的问题几乎都是同一原因：
**依赖清单不等于本机环境**。

排查方法：把实际用到的第三方包和 `requirements.txt` 对一遍。

```bash
docker exec ydsh-streamlit python -c "import openai, streamlit, pyhive, thrift_sasl; print('deps ok')"
```

现在 Dockerfile 里加了一行 `python -c "import flask, streamlit, pyhive, thrift_sasl, pymysql"`
做构建期自检，漏包会直接构建失败，而不是等到答辩现场提问才报错。

### 5.8 Streamlit 里图表区域空白，但页面没有任何报错

`components.html` 的 HTML 是 Python f-string 拼的，饼图标签格式串里写了 `\n`：

```python
label: {{ formatter: '{{b}}\n{{d}}%' }}   # ✗ Python 把 \n 变成了真实换行
```

生成的 JS 变成单引号字符串里夹了一个换行 → 整个内联脚本 `SyntaxError` →
图表容器是空的，而且错误只在 iframe 内部，Streamlit 主页面完全无感。

修正：用 `json.dumps` 编码后再注入，保证 JS 侧拿到的是转义的 `\n`。
诊断技巧：直接重放 iframe 里的脚本文本，把语法错误捞出来。

```python
f = [x for x in page.frames if x.url == "about:srcdoc"][0]
f.evaluate("() => { try { new Function(document.scripts[1].textContent)(); return 'ok'; }"
           " catch (e) { return e.name + ': ' + e.message; } }")
```

### 5.9 仪表板列表显示「没有数据」，直接开看板 URL 又被踢回列表

症状是这两个一起出现：`/dashboard/list/` 空白，点进 `/superset/dashboard/ydsh-sales-overview/`
立刻 302 回 `/dashboard/list/`（页面上还会闪过一句 flash 提示）。

容易误判成"数据没了 / 看板没建成"。实际库里记录齐全：

```bash
docker exec mysql mysql -uroot -proot -e \
  "select id, dashboard_title, slug, published from superset.dashboards;"
# 1  ...  ydsh-sales-overview  1
```

真正的原因是**没登录 + Public 角色缺数据集权限**。Superset 判定
「非管理员能否看看板」的规则是：

> 看板要么不依赖任何数据集，要么用户对它**至少一个数据集**有
> `datasource_access` 权限。（`superset/security/manager.py` 里
> `raise_for_access(dashboard=...)` 的 REGULAR RBAC 分支）

`PUBLIC_ROLE_LIKE = "Gamma"` 只把菜单级权限（Dashboard/Chart 的 can_read）补给了
Public，而**数据集权限是按表逐条授予的**（`[库].[表](id:N)` + `datasource_access`），
Gamma 默认一条都没有。于是匿名用户过不了这一关：看板 302、列表 count=0。

```bash
# 复现：匿名查列表
curl -s http://127.0.0.1:8088/api/v1/dashboard/ | python -c "import json,sys;print(json.load(sys.stdin)['count'])"
# 0
```

修正已写进 `apps/superset/provision.py` 的 `grant_public_read()`：只给仪表板实际
用到的 8 张 ADS 结果表授权，**不给** `all_datasource_access`，明细层 dwd/dws 仍然读不到，
匿名也只有读权限。重跑一次是幂等的（新增 0 条）。

```bash
python apps/superset/provision.py     # 幂等，含 [5] 免登录授权
curl -s http://127.0.0.1:8088/api/v1/dashboard/ | python -c "import json,sys;print(json.load(sys.stdin)['count'])"
# 1
```

授权后需要 `docker restart superset` 让权限缓存失效，否则仍返回 0。

> 生产环境不要这么做：答辩演示需要"打开就能看"，而真实项目里匿名读全量经营数据
> 是不可接受的，应当走 SSO 登录 + 行级权限。

## 六、停止、清理与重部署

```bash
docker compose stop                 # 停机保数据
docker compose down                 # 删容器保数据卷（下次 up 仪表板还在）
docker compose down -v              # 连卷一起删（元数据、数仓、仪表板全没，慎用）
docker compose up -d                # 重新拉起（不重建镜像）
docker compose up -d --build        # 改了代码/依赖后重建
docker compose logs -f hive-server  # 跟某个服务的日志
```

**备份**（换机器前必做）：

```bash
docker run --rm -v ydsh-dw_mysql_data:/data -v %cd%:/backup alpine \
  tar czf /backup/mysql_data.tar.gz -C /data .
docker run --rm -v ydsh-dw_warehouse:/data -v %cd%:/backup alpine \
  tar czf /backup/warehouse.tar.gz -C /data .
```

两个卷合计约 1.2 GB，恢复时反向解包到同名卷即可。

## 七、这套编排做了什么取舍

| 取舍 | 选择 | 理由 |
|---|---|---|
| app 与 streamlit | **共用一个镜像** | 两者共用 `python/` 查询层和 `nl2sql`，拆两个镜像要多拉 1 GB，且逻辑会分叉 |
| 图表数据源 | **MySQL（不是 Hive）** | 筛选器每动一次就要重算，Hive 一次 4 秒用户等不起；MySQL 26 ms |
| ClickHouse | 留在编排里但不接 Superset | Superset 4.1 的 `clickhouse+http` 方言加载失败（`ClickHouseEngineSpec` 找不到），不为一个驱动去改镜像；CH 仍用于压测对比 |
| Superset 元数据库 | **MySQL（不是 SQLite）** | SQLite 随容器重建消失，做好的仪表板会一起没 |
| Hive pid 清理 | 写进 `entrypoint` | 依赖 Docker Desktop 重启后的行为，手工清理无法固化 |
