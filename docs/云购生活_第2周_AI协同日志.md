## 记录 1｜先扫描再写映射，避免"按任务书举例写 case when"

- **我的提问**：任务书里列了 `gender（男/女/M/F/未知）`，我是不是照着写 case when 就行？
- **AI 回应**：不要照抄。先对每个枚举字段跑 `SELECT 字段, COUNT(*) GROUP BY 字段`，把实际取值全列出来再映射。任务书举例通常不全。
- **验证结果**：实扫出来 gender 有 8 种（含 `male`、`Female`、空串），member_level 有 12 种，order_status 有 12 种（含数字码 1/2/3/4），behavior_type 有 10 种。如果只按任务书举例写，会漏掉 `male` / `Female` / `WeChat` / `App` 这些首字母大写变体，实测漏掉的行数会超过 2,000。
- **落地**：`sql/clean/01_enum_map_seed.sql` 把扫描结果落进 `dq_enum_scan` 表，字典 `dim_enum_map` 共 68 条映射，并加了一段"字典覆盖率自检"（返回 0 行才算合格）。
- **结论**：**枚举清洗的第一步永远是扫描，不是写 case when。**

## 记录 2｜AI 建议的分位数阈值，直接照做会失效

- **我的提问**：手册说"用分位数（P99）而非绝对值设定阈值"，那我就 `percentile(pay_amount, 0.99)` 当上限？
- **AI 第一版回应**：对，用 P99 自适应。
- **验证结果（AI 错了）**：实测 `percentile(pay_amount, 0.99) = 5,510,776.62`。原因是 291 条百万级脏值本身就在样本里，把 P99 直接顶到了 550 万——**用污染过的分位数去识别污染，等于没洗**。商品价格同理（P99 = 410,186，而正常价最大只有 8,992）。
- **纠正做法**：先在明显正常的区间 `0 < pay_amount < 100000` 内算分位数，得到 P99 = 4,942.67、最大 4,999.85，据此把绝对阈值定在 **10,000**（留一倍余量防误杀）。
- **额外发现**：`percentile()` 在 Hive 4 只接受 `(bigint, double)`，传 `decimal` 列直接报 `NoMatchingMethodException`；换 `percentile_approx(cast(x as double), cast(0.99 as double))` 才行，而且第二个参数也得显式转 double。
- **结论**：**分位数可以自适应，但只能在没有脏值的子集上算。** 这条已写进《数据质量清洗报告》第 3.3 节。

## 记录 3｜生成 366 天日期维度，`sequence()` 不可用

- **我的提问**：Hive 里怎么生成一整年的时间维度？
- **AI 第一版回应**：用 `explode(sequence(to_date('2024-01-01'), to_date('2024-12-31'), interval 1 day))`。
- **验证结果（AI 错了）**：本环境 Hive 4.0.0 报 `SemanticException [Error 10011]: Invalid function SEQUENCE`，该 UDTF 未注册。
- **纠正做法**：改用"数字表交叉连接"——`(0..3) × (0..9) × (0..9)` 生成 0~399，过滤 `n <= 365`，再 `date_add('2024-01-01', n)`。不依赖任何版本特性，Hive 2.x+ 都能跑。
- **结果**：`dim_date` 生成 366 行（2024 是闰年），校验 2024-02-29 存在、2024-07-06 是周六、2024-11-11 是周一。
- **结论**：AI 给的语法在文档上成立，不代表在当前版本可用。**写完必须跑一次。**

## 记录 4｜`date_format(d,'u')` 返回的竟然是年份

- **现象**：生成时间维度时用 `date_format(d,'u')` 取星期几，结果 `day_of_week` 列全部是 `2024`，`weekday_name` 全是 NULL。
- **AI 排查**：`date_format` 的格式化符在不同 Hive 版本解释不一致，`'u'` 在这套环境里被解释成"年"（ISO year），不是"星期几"。
- **纠正做法**：改用 `dayofweek()`（1=周日 … 7=周六），换算成"1=周一 … 7=周日"：
  `pmod(dayofweek(d) + 5, 7) + 1`，周末判断用 `dayofweek(d) IN (1,7)`。
- **验证**：2024-07-06 正确得到"周六"、is_weekend=1。
- **结论**：**日期格式化符属于"看起来通用、实际各版本不同"的高危区**，能用数值函数就别用格式串。这个坑已写进 `00_ddl_dwd.sql` 的注释。

## 记录 5｜Git Bash 把 `/sql` 改成了 `C:/`，Hive 报 `No FileSystem for scheme "C"`

- **现象**：`docker exec ... beeline -f /sql/dwd/00_ddl_dwd.sql` 报 `No FileSystem for scheme "C"`，看起来像 Hive 的路径问题，实际是 shell 的问题。
- **AI 排查**：Git Bash（MSYS2）在传参时会把以 `/` 开头的路径自动转成 Windows 路径，`/sql/...` 被替换成了 `C:/Program Files/Git/sql/...`，beeline 拿到的是 `C:/...`，Hadoop 自然没有 `C` 这个 scheme。
- **纠正做法**：`MSYS_NO_PATHCONV=1` 前缀禁用路径转换。或者干脆用 `-f /dev/stdin < file.sql` 走标准输入。
- **结论**：**跨平台工具链的报错，先怀疑 shell，再怀疑程序。** 这个坑排查了将近 20 分钟。

## 记录 6｜`CREATE TABLE AS SELECT` 会丢字段注释，改用显式 DDL + INSERT

- **我的提问**：既然清洗结果就是一张新表，直接 `CREATE TABLE ... AS SELECT` 不是更省事？
- **AI 回应**：CTAS 确实省事，但会丢掉所有列注释（`COMMENT`），而且字段类型由 Hive 推断——`CASE WHEN` 出来的列容易被推成 `STRING`，金额列可能从 `DECIMAL(14,2)` 变成 `DECIMAL(38,18)`。
- **决策**：改为「`00_ddl_dwd.sql` 统一定义带注释的 DDL + 各清洗脚本 `INSERT OVERWRITE` 装载」。
- **额外收益**：`INSERT` 相当于 schema-on-write 校验，清洗表达式算出的类型和 DDL 不一致会当场报错，比 CTAS 静默推断安全。"改对没改对"从"看数据"变成"看有没有报错"。
- **结论**：**给人用的表必须写注释；能把错误提前到编译期的写法，优先选。**

## 记录 7｜质量报告第一版把修复率算成了 0%

- **现象**：`dq_compare` 第一次跑出来，"用户年龄缺失/越界"这一行是 `清洗前 78 / 清洗后 78 / 修复率 0.00%`，看起来像完全没洗。
- **原因（我的错）**：清洗后那一侧我写的是 `SUM(age_is_filled)`。但 `age_is_filled=1` 表示"**这一行被填充过**"，它恰恰等于清洗前的脏值数 78，不是清洗后剩余的问题数。拿它当分母对面的减数，等于自己减自己。
- **纠正做法**：清洗后改为 `SUM(IF(age IS NULL OR age < 1 OR age > 120, 1, 0))`，得到 0，修复率 100%。
- **AI 的贡献**：它没有直接改，而是问我"这 78 是修好的数量还是没修好的数量？"——这个反问让我自己发现标记位和问题数是两个方向。
- **结论**：**标记位（flag）不能直接当指标用。** 标记位回答"处理过没有"，指标要回答"问题还剩多少"，两者方向相反，混用必然出错。

## 记录 8｜明细金额和订单实付差 11 倍，品类分析差点做错

- **现象**：算品类销售分布时，八个品类合计 3.05 亿，而总 GMV 只有 2,734 万。
- **AI 排查**：不是 SQL 写错，是数据本身不对账——明细 `unit_price`（商品级定价，均值约 3,800）和订单 `pay_amount`（均值约 2,529）不是同一套逻辑生成的。已付款订单的明细金额合计是订单实付的 **11.19 倍**。
- **纠正做法**：品类 GMV 改为**按明细金额占比分摊订单实付**：
  `品类GMV = Σ( order.pay_amount × 该行明细金额 / 该订单明细金额合计 )`
  这样八品类 GMV 之和正好等于总 GMV，报表能对平。
- **结论**：**对不上账的数据不能硬汇总，要换口径。** 这条同时写进了 EDA 简报的"数据可信度核查"。

## 记录 9｜MAPJOIN 提示写错位置，整个脚本挂掉

- **现象**：`LEFT JOIN /*+ MAPJOIN(u) */ (SELECT ...) u` 报 `ParseException ... cannot recognize input near ' MAPJOIN(u) '`。
- **原因**：Hive 的 hint 必须紧跟 `SELECT` 关键字，不能挂在 JOIN 后面。
- **纠正做法**：与其纠结 hint 位置，不如直接去掉——维度表只有 60~1000 行，Tez 会自动做 Map-Side Join 广播小表，手写提示属于多余优化。
- **结论**：**优化器提示是"锦上添花"，写错就变"雪上加霜"。** 先让 SQL 正确，再谈优化。

## 记录 10｜分桶表：能用，但在本数据量下没用

- **我的提问**：任务书要求"尝试分桶表的使用"，分桶到底带来多少性能提升？
- **AI 回应**：分桶的收益在"同键 JOIN 免 Shuffle"和"桶内抽样"，前提是数据量足够大（单表 GB 级以上）。1.5 万行订单分 8 桶，每桶不到 2,000 行，Shuffle 本来就是秒级，收益测不出来。
- **我的处理**：不虚构性能数字，只做三件可验证的事——① 桶数为 8（`DESCRIBE FORMATTED` 确认）；② 8 个桶文件行数 1,611~2,283，哈希散列均匀；③ 自连接跑通，产生 240,908 行，说明 bucket map join 可用。
- **答辩口径**："分桶我们做了技术验证，能跑通、分布均匀；但当前数据量下不产生实际性能收益，所以我们没有把分桶表作为主表，只保留 `dwd_order_bucketed` 作为验证样本。"
- **结论**：**"能用"和"有用"是两件事，分开讲比硬吹更可信。**

**最有价值的一条经验**：AI 最擅长的不是"给答案"，而是"在你写错的时候问一句为什么"。上面 5 次纠错里，有 2 次是它反问、我自己想通的——这种纠错比直接给正确答案记得牢。反过来说，它给的"标准写法"（`sequence()`、`percentile()`）在这个具体环境里都会翻车，所以**任何 AI 给的 SQL 都必须在本机跑一遍再写进交付物**。
