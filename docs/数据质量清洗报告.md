## 3. 问题清单与处理策略

### 3.1 缺失值（3 项）

| 字段 | 缺失/异常量 | 策略 | 依据 |
|---|---:|---|---|
| user.age | 78（NULL 51 + 负数 4 + 0 值 8 + 200 值 15） | 用有效样本均值 **41** 填充，打 `age_is_filled=1` | 维度表删行会导致该用户全部订单变成"孤儿事实"，代价远大于年龄偏差 |
| user.email | 193（19.3%） | **保留 NULL**，打 `email_is_missing=1` | 无任何字段可推断邮箱，编造数据比留空危险得多 |
| product.launch_date | 11 | **保留 NULL**，打 `launch_date_is_missing=1` | 上架日期与价格/品类无稳定关系，插补等于伪造 |

**为什么缺失值修复率只有 27.66% 还要写进报告**：把"修不了"如实写出来，比硬凑一个 100% 更符合数据治理的职业规范。真实项目里邮箱、上架日期这类无推断依据的缺失，标准做法就是保留 + 标记 + 在下游计算时用 `WHERE ... IS NOT NULL` 显式排除。

### 3.2 重复值（1 项）

| 对象 | 重复量 | 策略 |
|---|---:|---|
| ods_order | 600 行（586 组：388 组整行完全重复 + 198 组主键相同但其余字段不同） | 按 `order_id` 去重，保留 1 行 |

**去重排序规则（决定 198 组"冲突重复"留哪条）**：

```
ROW_NUMBER() OVER (
  PARTITION BY order_id
  ORDER BY IF(pay_amount > 0 AND pay_amount <= 10000, 0, 1) ASC,  -- ① 金额合法优先
           order_time DESC,                                        -- ② 时间更新优先
           pay_amount DESC                                         -- ③ 兜底，保证结果确定
)
```

① 优先留金额合法的，避免把刚清洗好的数据又留成脏的；② 业务上后写覆盖先写（binlog 消费顺序）；③ 兜底是为了**结果可复现**——同一份数据跑两次必须得到同一结果，这是 ETL 的基本要求。

### 3.3 异常值（8 项）

| 字段 | 异常量 | 判定阈值 | 策略 |
|---|---:|---|---|
| order.pay_amount | 310 负 / 312 超大 | 负值；> 10000 | 负值取绝对值；超大值用**同门店正常订单金额中位数**替换 |
| order.discount_amount | 769 负 | < 0 | 置 0（负优惠无业务含义） |
| product.price | 20 负 / 16 超大 | 负值；> 10000 | 负值取绝对值；超大值用**同二级品类正常价格中位数**替换 |
| order_item.quantity | 718（0 或负） | ≤ 0 | 为 0 剔除（386）；为负取绝对值（332） |
| order_item.quantity | 363 超大 | > 5 | 用**同商品正常区间中位数**替换（原值全部为 99） |
| order_item.unit_price | 798 负 | < 0 | 取绝对值 |

**阈值怎么来的（这是本报告最需要讲清楚的一点）**：

任务书建议"用分位数（P99）而非绝对值设定阈值"。直接照做会翻车：

| 字段 | 全表 P99 | 正常子集 P99 | 说明 |
|---|---:|---:|---|
| pay_amount | 5,510,776.62 | 4,942.67 | 291 条百万级脏值把 P99 顶到 550 万，按它清洗等于没洗 |
| price | 410,186.42 | 8,917.92 | 同理，脏值污染了分位数本身 |

正确做法是**先在明显正常的区间内算分位数，再确定绝对阈值**：

- 订单金额：`0 < pay_amount < 100000` 子集 P50=2,494、P95=4,741、P99=4,943、最大值 4,999.85 → 正常上限约 5,000，取 **10,000** 作为保守阈值（留 1 倍余量，避免误杀大额订单）。
- 商品价格：`0 < price < 100000` 子集 P99=8,917、最大 8,992.57 → 同样取 **10,000**。
- 明细数量：正常子集 1~5（P99=4.95、最大 5），异常值全部为 99 → 取 **>5 为异常**，且 6~90 区间实测 0 行，说明阈值无灰区。
- 年龄：业务常识 + 数据分布，取 **[1, 120]**。

**为什么用"同组中位数"而不是全局均值**：门店 A 的客单价长期 4,000，门店 B 只有 1,500，用全局中位数替换会把 A 的异常单改成"偏低"、把 B 的改成"偏高"。按最细可用维度（门店 / 二级品类 / 商品）分组取中位数，替换后的值仍然符合该组的业务量级。

### 3.4 格式不一致（5 项）

| 字段 | 不一致量 | 原始写法 | 统一为 |
|---|---:|---|---|
| order.order_date | 1,902 | `2024-07-26` / `2024/07/26` | `yyyy-MM-dd` |
| user.register_date | 125 | 上述两种 + `20240726` | `yyyy-MM-dd` |
| user.phone | 102 | `13892127520` / `138-9212-7520` | 11 位纯数字 |
| user_behavior.behavior_time | 6,088 | `2024-11-05 10:20:30` / `2024/11/14 00:13`（缺秒） | `yyyy-MM-dd HH:mm:ss`，缺秒补 `:00` |
| product.category | 27 | `数码家电 `（尾空格） → 16 种取值 | `trim()` 后收敛为 8 种 |

**实现方式**：日期用三分支 `CASE WHEN`（8 位纯数字 → 手工拼横杠；否则把 `/` 换成 `-`）。没有用 `to_date()` 或 `unix_timestamp()` 做隐式转换，因为不同 Hive 版本对 `20240726` 的解析行为不一致，而显式分支在任何版本上都稳定。

**缺秒补 `00` 是精度降级，不是修复**：所以单独打 `time_is_fixed=1` 标记，做"小时分布""天级趋势"不受影响，做"秒级并发"就必须排除这些行。

### 3.5 业务逻辑错误（6 项，枚举取值不规范）

| 字段 | 不规范量 | 原始取值种类 | 规范值域 |
|---|---:|---:|---|
| user.gender | 498 | 8 | 男 / 女 / 未知 |
| user.member_level | 108 | 12 | 普通 / 银卡 / 金卡 / 钻石会员 + 未知 |
| order.order_status | 1,375 | 12 | 待支付 / 已支付 / 已完成 / 已取消 / 退款中 |
| order.pay_type | 651 | 7 | 支付宝 / 微信支付 / 银行卡 / 货到付款 |
| order.channel | 310 | 6 | APP / 小程序 / PC官网 / 门店 |
| user_behavior.behavior_type | 57,551 | 10 | 浏览 / 加购 / 收藏 / 购买 |

**方法：先扫描、再映射、后校验**，三步缺一不可。

1. **扫描**：`SELECT 字段, COUNT(*) GROUP BY 字段`，把每一种写法都列出来（结果落在 `dq_enum_scan` 表）。为什么必须扫描？因为任务书举例只提到 `男/女/M/F/未知`，实际数据里还有 `male`、`Female`、空串——只按任务书举例写 `case when` 一定会漏。
2. **映射**：把 68 种脏写法写成规范字典 `dim_enum_map`，ETL 的 `case when` 分支与字典一一对应。
3. **校验**：`08_verify_after_clean.sql` 反向检查"DWD 里是否还存在规范值域以外的取值"，返回 0 行才算通过。

**行为类型为什么改动量最大（96%）**：`pv/buy/cart/fav` 英文缩写占 57,551 行，中文只占 2,449 行。也就是说这个字段"脏"的不是少数派，而是主流量。仍然统一成中文，理由是订单状态、支付方式、渠道的标准值都是中文，如果行为类型保留英文，下游做"全站行为口径"时会出现"pv 和 浏览 到底是不是一个东西"的歧义。改动量大的风险由值域校验兜住（4 类取值、60,000 行零异常）。

### 4.3 一个必须说清的口径细节

订单负金额清洗前 310 条、超大金额 312 条，合计 622 条；但 DWD 侧实际只修正了 **596 条**（SIGN_FIXED 297 + OUTLIER_REPAIRED 299）。

答辩时被问到"为什么 310 + 312 ≠ 297 + 299"，答这一条即可。

## 7. 可追溯性设计

数据治理的核心不是"改对"，而是"改得对、也说得清"。本项目三道保障：

1. **原值留档**：`pay_amount_raw`、`quantity_raw` 保存被修正前的原始值。
2. **修正标记**：`amount_flag`、`qty_flag`、`price_flag` 三态标记（`NORMAL` / `SIGN_FIXED` / `OUTLIER_REPAIRED`），可随时筛出"被改过的行"核对。
3. **ODS 不动**：所有清洗只写 DWD，ODS 永远保留原始快照。任何一次清洗都能被完整重放。

验证示例（可以随时抽查被修正的订单）：

```sql
SELECT order_id, pay_amount_raw, pay_amount, amount_flag
FROM ydsh_dwd.dwd_order
WHERE amount_flag <> 'NORMAL'
LIMIT 10;
```
