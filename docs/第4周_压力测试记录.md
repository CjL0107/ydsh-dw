## 二、统计口径（先说清楚，避免数字被误读）

1. **SQL 侧**每档跑 1 次预热 + 3 次正式，取**中位数**。首次查询要编译 Tez DAG、
   拉容器，只看第一次会把耗时高估 3~5 倍。
2. **接口侧**按「固定 200 请求 / 并发数」跑，不用固定时长 —— 固定时长会让慢档
   样本偏少，P95 失真。
3. **失败请求单独计数**，不计入延迟分位数。混进去算平均会把「超时 30 秒」和
   「成功 15 毫秒」摊成一个漂亮的假数字。

## 三、查询优化对比

### 3.1 四组用例

| 用例 | 查询路径 | 引擎 | 中位耗时(ms) | 返回行数 |
|---|---|---|---:|---:|
| **A** | *分区裁剪：谓词能否下推到分区列* | | | |
| A1 | 分区裁剪 · 开启（`order_date = '2024-04-12'`） | hive | 3514.8 | 1 |
| A2 | 分区裁剪 · 关闭（`substr(order_date,1,10) = ...`） | hive | 3557.7 | 1 |
| **B** | *列裁剪：列存读 1 列 vs 读全部列* | | | |
| B1 | 只读 1 列（`sum(pay_amount)`） | hive | 3637.1 | 1 |
| B2 | 读全部 17 列（`select *` 子查询再聚合） | hive | 3688.5 | 1 |
| **C** | *数据倾斜：直接 group by vs 加盐两阶段* | | | |
| C1 | 直接 `group by store_id`（含大店倾斜） | hive | 3745.2 | 34 |
| C2 | 加盐两阶段（`store_id + rand()*4`） | hive | 3674.3 | 34 |
| **D** | *三层选型：同一业务问题的四条取数路径* | | | |
| D1 | 省 GMV · Hive 明细现算（join 维表） | hive | 4207.7 | 13 |
| D2 | 省 GMV · Hive ADS 预聚合 | hive | 3546.3 | 10 |
| D3 | 省 GMV · **MySQL** ADS（仪表板数据源） | mysql | **26.8** | 10 |
| D4 | 省 GMV · **ClickHouse** ADS | clickhouse | **7.7** | 10 |

### 3.2 结论一：这个数据量下，A/B/C 三组的墙钟时间说明不了问题

三组的倍数关系只有 **1.01× / 1.01× / 1.02×**，看起来「优化没用」。**结论恰恰相反** ——
看绝对数字：所有 Hive 查询都落在 3.5~3.7 秒这个窄区间里，连只读一列的 B1 都要 3.6 秒。
一条 1.5 万行、单分区的 `count(1)` 不可能真要 3.5 秒，这 3.5 秒是：

- Tez session 启动（AM 容器拉起、DAG 编译）
- YARN 分配 container

也就是说，**固定开销把可变开销彻底淹没了**。在这个量级下测执行计划的优劣，
量的是 Tez 启动速度，不是扫描速度。用墙钟时间证明「分区裁剪有效」是不成立的，
必须换成扫描量的证据。

### 3.3 结论二：用结构证据量化裁剪收益

| 指标 | 值 |
|---|---|
| 分区总数 | **366** |
| 全表行数 | 15,000 |
| 单分区行数（基准日 2024-04-12） | 60 |
| 裁剪后需扫描 | 1 个分区 |
| 理论 IO 节省 | **99.7%** |
| 扫描行数倍数 | **250×** |

即：`where order_date = '...'` 只读 1/366 的目录，`where substr(order_date,1,10) = '...'`
必须扫完 366 个目录。**收益是真实的 250 倍扫描量差**，只是在这台机器上被 3.5 秒的
启动开销盖住了。换算到千万行量级（单次扫描本身就要几十秒），这个差距会直接体现在
响应时间上。

> 附带发现：`EXPLAIN` 在 Hive 4 的 Tez 计划里**不打印裁剪到的分区列表**，
> 且两种写法的 `TableScan rows` 完全相同（都是 60）—— 因为表上没收集列统计信息，
> CBO 只能瞎猜。所以「看 EXPLAIN 判断有没有裁剪」这条路在这里是走不通的，
> 得回到分区数/文件数这种物理证据。

### 3.4 结论三：加盐是负优化，不该无条件上

C2（加盐两阶段）只快了 1.02×，而且在上一轮单独重跑时是 **0.92×（更慢）**。
原因很直接：加盐把一次 shuffle 变成两次，小数据量下 shuffle 的额外开销大于
倾斜带来的不均衡。

**所以这次没有把加盐写进生产 SQL。** `dwd_order` 只有 1.5 万行、34 家门店，
最大店和最小店的差距不足以让单个 reducer 成为瓶颈。加盐的适用条件是
「单 key 数据量超过 reducer 处理能力」，本场景不满足 —— 提前优化反而拖慢。

这一条比"加盐快 N 倍"更值得写进报告：**优化的前提是诊断，不是套路**。

### 3.5 结论四：真正拉开差距的是分层，不是单条 SQL 的写法

| 路径 | 耗时 | 相对 D1 |
|---|---:|---:|
| D1 Hive 明细现算（join 维表） | 4207.7 ms | 1× |
| D2 Hive ADS 预聚合 | 3546.3 ms | 1.2× |
| D3 MySQL ADS | 26.8 ms | **157×** |
| D4 ClickHouse ADS | 7.7 ms | **546×** |

- **D1 → D2 只有 1.2×**：即便走预聚合表，只要还在 Hive 里，就逃不过 Tez 启动开销。
- **D2 → D3 是 132×**：把 421 行结果搬到 MySQL，响应从 3.5 秒掉到 27 毫秒。
- **D3 → D4 再快 3.5×**：列存在这个量级仍有优势（只读 2 列 vs 行存读整行）。

这就是仪表板数据源选 MySQL、ClickHouse 留作对比基线的全部理由：
**用户感知的"快"，来自把计算提前做完，不是把 SQL 写得更花。**

## 四、接口并发压测

### 4.1 结果

| 并发数 | 请求数 | 成功 | 失败 | QPS | P50(ms) | P95(ms) | 最大(ms) |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 | 200 | 200 | 0 | 48.4 | 15.3 | 36.2 | 42.0 |
| 5 | 200 | 200 | 0 | 281.9 | 16.1 | 30.0 | 40.1 |
| 20 | 200 | 200 | 0 | **428.0** | 44.4 | 51.7 | 58.7 |
| 50 | 200 | 200 | 0 | 418.6 | 90.3 | 117.9 | 135.9 |

测试端点轮转：`/api/overview`、`/api/trend`、`/api/province`、`/api/category`。
800 个请求**零失败**。

### 4.2 容量结论

- **饱和点在 20 并发**：QPS 从 281（并发 5）爬到 428（并发 20），再加到 50 并发
  反而略降到 418 —— 单进程 Flask 已到瓶颈，加并发只是把队列排长。
- **延迟走势符合预期**：并发 20 → 50，P50 从 44 ms 涨到 90 ms（约 2 倍），
  P95 从 52 ms 涨到 118 ms。没有出现延迟爆炸，说明没有锁竞争/连接池耗尽。
- **P95/P50 比值健康**（1.2~1.3），说明尾部没有偶发的长阻塞。

### 4.3 瓶颈在哪、怎么扩

| 层 | 现状 | 扩展方式 |
|---|---|---|
| Flask 进程 | 单进程 + `threaded=True`，GIL 限制 | `gunicorn -w 4 -k gthread --threads 8`，配 Nginx 反代 |
| 数据来源 | 读本地 29 KB JSON，已全部缓存进内存 | 无需扩展；若改实时查库，需加 Redis 缓存 |
| Hive | 不参与在线请求（快照解耦） | 在线 QPS 与 Hive 完全无关，这是快照设计的最大收益 |

> 换句话说：**大屏接口的性能上限与数据仓库无关**。43 秒的重算在离线阶段完成，
> 在线只读文件。10 个面板的看板，20 并发下 P95 51.7 ms，完全够用。

## 五、已知局限（如实记录）

1. **单机环境**：Hive、MySQL、ClickHouse、Superset 全在一台笔记本的 Docker 里，
   互相抢 CPU/IO，压测数字不能直接外推到生产集群。
2. **数据量小**：1.5 万行不足以暴露真实的分区裁剪/列裁剪差异（见 3.2）。
   要拿到有说服力的时间差，需要百万级以上数据。
3. **接口压测是读快照**，不代表「实时查 Hive」的性能。后者在第 3 周测过：
   单次 4.2 秒，10 并发就会把 Hive 打满。
4. **未做长时间稳定性测试**（如 1 小时持续压测看内存增长）。当前是功能验证
   级别的压测。
5. **加盐结论只对本数据集成立**：换到真实订单量级（单店百万单）需要重新测，
   不能因为"这次没用"就否定加盐。
