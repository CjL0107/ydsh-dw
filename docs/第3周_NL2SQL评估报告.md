把 42 个被静默丢弃的字段补回去之后，同一个模型、同一套题集、同样的 `temperature=0`，人工判定从 5/8 变成 7/8。这意味着上一轮报告里"模型爱漏列、爱猜错"的归因有一半是错的——**它漏的列，我们根本就没告诉过它。**

## 二、根因：一行 CSV 解析吃掉了所有 decimal 列

`hive_runner.describe()` 用 `--outputformat=csv2` 取 Hive 的字段元信息。Hive 的 `DESCRIBE` 输出长这样：

```
col_name,data_type,comment
channel,string,渠道
gmv,decimal(16,2),GMV          ← 类型名里有一个逗号
gmv_share,decimal(10,4),GMV 占比
```

`csv.reader` 把 `gmv,decimal(16,2),GMV` 切成 **4** 段，而表头只有 **3** 列，长度不等 → 计入 `bad` → 直接丢弃该行。四个 decimal 列（`gmv` / `gmv_share` / `aov` / `metric_value`）在 14 张表里被丢得干干净净。

最要命的是它是**静默**的：

- 原来的兜底只判「一行都没对齐」才抛异常；部分行对不齐完全无声无息。
- `nl2sql_schema.py` 打印的是 `抽取 ydsh_ads.ads_channel_contribution: 4 个字段`——这个 4 看起来完全正常，没人会去数一个 7 列的表为什么只抽到 4 列。
- 于是 `schema.json` 从 112 列变成 70 列，Prompt 里**缺了所有指标列**，而模型只能看到 `channel`、`order_cnt`、`user_cnt` 这些描述性字段。

**整个项目天天在算 GMV，而模型从头到尾没在 schema 里见过 `gmv` 这一列。** 它上一轮"漏查 `metric_value`"、"选了 `order_cnt` 而不是 `gmv_share`"，不是判断失误，是它眼前只有这几列可选。

对比修复前后：

| | 修复前 | 修复后 |
|---|---|---|
| Schema 字段数 | 70 | **112** |
| 缺失列 | 42 列，覆盖全部 14 张表 | 0 |
| 典型缺失 | `gmv`、`gmv_share`、`aov`、`mom_rate`、`cancel_rate`、`metric_value`、`avg_unit_price`、`gmv_dod`、`gmv_ma7` | — |

修复动作两处：

1. `describe()` 改用 `--outputformat=tsv2`，用 Tab 分隔，类型名里的逗号不再是分隔符。
2. `run_sql()` 增加部分行对不齐时向 stderr 告警——这类静默丢失必须先叫出来，哪怕不中断执行。

这件事和上一轮那个"假 8/8"是同一类问题：**静默返回不完整的结果，比直接报错危险得多。** 报错会被看见，少一半列的 schema 会被当成正常。

## 四、仍然存在的问题

**1. 「销量」的歧义没有解决（部分正确）**

```sql
SELECT rank_no, category, gmv FROM ydsh_ads.ads_category_top10
WHERE rank_no <= 5 ORDER BY rank_no
```

`rank_no` 在 ETL 里是 `ROW_NUMBER() OVER (ORDER BY gmv DESC)`，即按 GMV 排名。题目问"销量最高"，若销量指件数，答案应是另一组品类。模型既没按件数重排，也没澄清歧义，属照搬现成排名。

更值得注意的是：判据给了它「一致」，因为参考 SQL 也这么写——**参考 SQL 本身带着这个歧义**。判据一致不代表语义正确，这就是必须保留人工复核这一列的原因。

**2. 复购率 100% 是数据特征，不是算错**

1000 个用户全部 `order_cnt > 1`，所以复购率必然是 100%。这个数字看起来像算错，实际上要回到数据本身去解释，写进报告时得说清楚。

**3. 执行成功 ≠ 答案正确**

修复后 8/8 执行成功、8/8 宽松一致，但仍有 1 题语义存疑。「SQL 跑通了」和「答案对了」之间依然没有必然关系，而前者最容易做进监控看板、看起来最漂亮。

## 五、`temperature=0` 不等于确定性

同一套题集连跑两轮（`temperature=0`），8 题里 **4 题的 SQL 被改写**：

| # | 第一轮 | 第二轮 |
|---|--------|--------|
| 2 客单价 | `SUM(gmv)/SUM(paid_order_cnt)` 自算 | 查元信息列，漏 `metric_value` |
| 3 品类 Top5 | 选 `order_cnt, item_qty` | 选 `gmv, item_qty` |
| 5 复购率 | `metric_name='复购率' OR metric_key='repurchase_rate'`（后者不存在） | 自己写 `CASE WHEN order_cnt>1` 算 |
| 7 最近 7 天 | 子查询内加 `stat_date LIKE '2024-%'` | 去掉了这个过滤 |

两个结论：

**1. `temperature=0` 不等于确定性。** "确定性输出"在有采样成分的服务上并不成立，所以"我跑了一次，正确率 X%"这种结论，误差可能比结论本身还大。

**2. 单次评测的正确率不可信。** 5/8 → 7/8 的变化里有 2 题是修复带来的真实提升（第 2、4 题），但第 1、5 题的写法仍在两轮之间来回变。要把 7/8 当稳定值引用，至少得跑 3~5 次取均值与方差。**本报告的数字只代表这一次运行。**

## 六、防御措施：哪些已经做了，哪些还缺

### 已经实现

| 措施 | 位置 | 挡住什么 |
|------|------|----------|
| SQL 白名单校验 | `nl2sql.validate_sql` | 只放行 SELECT、只许引用授权表，挡住 DROP / 跨库读取 |
| 失败自愈重试 | `nl2sql.ask` | 把 Hive 报错原文回灌给模型改一版，最多 2 次 |
| 参考 SQL 双轨比对 | `validate_llm.same_result` | 挡住"结果碰巧像"的情况（严格/宽松双判据） |
| 人工复核留痕 | `llm_eval_review.json` | 挡住"用程序结论代替人判断" |
| 维度值注入 | `nl2sql_schema.DIM_SPECS` | 8 维度 108 个真实取值进 Prompt，灭掉"广东/广东省"这类等值匹配错 |
| 维度字面量校验 | `nl2sql.check_dim_literals` | 模型写出库里不存在的维度值时告警（`LIKE` 放行） |
| 执行器失败可见 | `hive_runner.run_sql` | 容器不可用/表头错位/部分行对不齐都不再静默返回空 |

### 还缺的，按性价比排序

**① 结果健全性校验（最该补）**
返回 0 行、全 NULL、或数值列全为空 → 判定可疑并重试。上一轮"漏查 `metric_value`"那题，光靠这个就能拦住，因为它根本不看内容对不对，只检查"有没有内容"。

**② 多次采样 + 投票**
同一问题跑 3 次，取结果一致的 SQL 执行。既然不确定性是既定事实，就用重复换稳定。

**③ Schema 完整性自检**
抽取完成后校验「每张表抽到的列数 == `SHOW COLUMNS` 的真实列数」，不一致就报错。这次的 42 列丢失如果有这一条，第一轮就会被拦住。**这是本轮最该加的护栏，因为它防的是"自己骗自己"。**

## 七、和规则兜底的对比

第 3 周前半段没有 Key，NL2SQL 走的是关键词规则兜底。两者不是替代关系：

| | 规则兜底 | 大模型 |
|---|---|---|
| 表达覆盖 | 只认预设问法，换个说法就失效 | 能理解同义表述、复杂条件组合 |
| 可预测性 | 完全确定，同样的输入永远同样输出 | 同样输入可能给出不同 SQL |
| 错法 | 规则写错（曾把"最近 7 天每日下单量"误匹配到 GMV 汇总） | 漏列、猜错维度值、照搬口径 |
| 排查成本 | 看代码就知道错在哪 | 要看生成的 SQL 才知道，且下次可能不复现 |

规则兜底我也修过 bug：**"最近 7 天每天的下单量"曾被单指标关键词抢先匹配成 GMV 汇总**，是加了时间序列意图分支才修好的。所以"规则更可靠"这个说法要看实现水平，不成立。

实际可用形态应该是规则打底 + 模型兜住长尾 + 结果校验兜住模型——三层都要。
