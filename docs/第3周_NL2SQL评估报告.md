| 判据 | 结果 | 这个判据回答什么 |
|------|------|------------------|
| 执行成功 | **8/8** | SQL 能不能在 Hive 上跑通 |

"SQL 跑通了"和"答案对了"之间没有必然关系，而前者最容易做进监控看板、看起来最漂亮。

## 二、三道错题与一道半对题

### 错题 1：漏了要查的那一列（客单价）

```sql
SELECT metric_key, metric_name, unit, definition
FROM ydsh_ads.ads_kpi_summary
WHERE metric_name LIKE '%客单价%'
```

表选对了、过滤条件选对了，**唯独没把 `metric_value` 查出来**。结果返回 1 行，全是元信息，没有数值。

这是我认为最危险的一类错误：行数非空、无报错、执行成功，表面完全正常，唯独答案不在里面。
如果只看"SQL 跑通率"或"是否返回了行"，这题会被判为通过。

### 错题 2：把用户的话当成字段里的值（广东省）

```sql
SELECT ROUND(SUM(gmv), 2) AS gmv
FROM ydsh_dws.dws_sales_store_day
WHERE province = '广东'          -- 实际取值是「广东省」
  AND stat_date BETWEEN '2024-01-01' AND '2024-12-31'
```

等值匹配 0 行，`SUM` 返回 NULL。正确写法是 `LIKE '%广东%'`。
这道题在题集里本来就标注了「易错点：写成 = '广东' 而非 LIKE」——模型如预期地踩了。

### 半对题：照搬现成排名，不追问口径（品类 Top5）

```sql
SELECT rank_no, category, gmv, item_qty
FROM ydsh_ads.ads_category_top10
WHERE rank_no <= 5 ORDER BY rank_no
```

`rank_no` 在 ETL 里是 `ROW_NUMBER() OVER (ORDER BY gmv DESC)`，按 GMV 排的。
题目问"销量最高"，模型返回的是"GMV 前 5 名及其件数"，既没按件数重排，也没向用户澄清"销量"指什么。

题目本身有歧义（销量 = GMV 还是件数），但模型的职责不该是挑一个解释然后沉默。

### 不算错的"不一致"：多查了一列（渠道占比）

```sql
SELECT channel, gmv, gmv_share FROM ydsh_ads.ads_channel_contribution ORDER BY gmv DESC
```

严格判据判它不一致，只因多带了一列 `gmv`——比只给占比更有用，不是错。
这也是我给脚本补"宽松判据"的原因：**判据过严会把好答案算成坏答案，和判据过松一样有害。**

## 三、比错题更值得说的一件事：同一道题，两次跑出不同 SQL

题集连跑两遍（`temperature=0`），8 题里 **4 题的 SQL 被改写**：

| # | 第一次 | 第二次 |
|---|--------|--------|
| 2 客单价 | `SUM(gmv)/SUM(paid_order_cnt)` 自算 → **对** | 查元信息列，漏 `metric_value` → **错** |
| 3 品类 Top5 | 选 `order_cnt, item_qty` | 选 `gmv, item_qty` |
| 5 复购率 | `WHERE metric_name='复购率' OR metric_key='repurchase_rate'`（后者不存在，靠中文名兜住） | 自己写 `CASE WHEN order_cnt>1` 算 → 口径自洽、对 |
| 7 最近 7 天 | 子查询内加 `stat_date LIKE '2024-%'` | 去掉了这个过滤 |

由此得到两个结论：

**1. `temperature=0` 不等于确定性。** 官方文档说的"确定性输出"在有推理/采样成分的模型上并不成立。
所以"我跑了一次，正确率 X%"这种结论，误差可能比结论本身还大。

**2. 单次评测的正确率不可信。** 这一轮 5/8，上一轮我按同样的口径复核是 6/8（客单价那题自算是对的），
相差 12.5 个百分点，全部来自同一道题的一次改写。要给出可信数字，至少得跑 3~5 次取均值与方差。

我把这个现象写进报告，而不是把跑得好的那次拿出来交差——后者是选择性汇报，比 5/8 难看得多。

## 四、防御措施：哪些已经做了，哪些还缺

### 已经实现

| 措施 | 位置 | 挡住什么 |
|------|------|----------|
| SQL 白名单校验 | `nl2sql.validate_sql` | 只放行 SELECT、只许引用授权表，挡住 DROP / 跨库读取 |
| 失败自愈重试 | `nl2sql.ask` | 把 Hive 报错原文回灌给模型改一版，最多 2 次 |
| 参考 SQL 双轨比对 | `validate_llm.same_result` | 挡住"结果碰巧像"的情况（严格/宽松双判据） |
| 人工复核留痕 | `llm_eval_review.json` | 挡住"用程序结论代替人判断" |

### 还缺的，按性价比排序

**① 维度值注入（最该做，成本最低）**
把 `province`、`channel`、`category` 的 `DISTINCT` 取值塞进 Prompt。
模型不知道"广东"在库里叫"广东省"，但它不需要知道——只要告诉它有哪些值。这一条能直接灭掉第 2 类错题。

**② 结果健全性校验（最难做,但不做等于没防线）**
返回 0 行、全 NULL、或数值列全为空 → 判定为可疑并重试。第 1 类错题（漏查 `metric_value`）
光靠这个就能拦住，因为它根本不检查内容对不对，只检查"有没有内容"。

**③ 指标口径固化**
客单价、复购率这类指标不该让模型自由发挥，应该在 Prompt 的 Few-shot 里明确
"这类问题一律查 `ads_kpi_summary` 的 `metric_key`，不要自己算"。
第 5 题两次跑出两种算法，都算出 100%，这掩盖了"指标口径可能漂移"的隐患。

**④ 多次采样 + 投票**
同一问题跑 3 次，取结果一致的 SQL 执行。既然不确定性是既定事实，就用重复换稳定。

## 五、和规则兜底的对比

第 3 周前半段没有 Key，NL2SQL 走的是关键词规则兜底。两者不是替代关系：

| | 规则兜底 | 大模型 |
|---|---|---|
| 表达覆盖 | 只认预设问法，换个说法就失效 | 能理解同义表述、复杂条件组合 |
| 可预测性 | 完全确定，同样的输入永远同样输出 | 同样输入可能给出不同 SQL |
| 错法 | 规则写错（曾把"最近 7 天每日下单量"误匹配到 GMV 汇总） | 漏列、猜错维度值、照搬口径 |
| 排查成本 | 看代码就知道错在哪 | 要看生成的 SQL 才知道，且下次可能不复现 |

规则兜底我也修过 bug：**"最近 7 天每天的下单量"曾被单指标关键词抢先匹配成 GMV 汇总**，
是加了时间序列意图分支才修好的。所以"规则更可靠"这个说法要看实现水平，不成立。

实际可用形态应该是规则打底 + 模型兜住长尾 + 结果校验兜住模型——三层都要。
